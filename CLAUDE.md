# Operating this VPS

Read this before touching anything on the server. It is written for Claude Code
and Hermes running *on* the VPS, which is the intended way to manage it.

## Ground rules

- **Never edit files under `/etc/nginx/sites-available/` by hand.** They are
  regenerated by `install/80-nginx.sh` from `stack/nginx/site.conf.template`.
  Certbot's additions are the one exception — it edits those files in place,
  and re-running stage 80 will drop the TLS blocks it added. If you must
  re-render, re-run stage 90 afterwards.
- **Never edit `stack/stack.env`.** It is generated from `vps.conf`. Change
  `vps.conf` and re-run stage 60.
- **Never `git reset --hard` or `git checkout -f` in `$REPOS_DIR`.** Someone
  may have hotfixed a file directly on the server. `ops/deploy.sh` deliberately
  refuses to fast-forward a diverged checkout for exactly this reason; respect
  the refusal, look at `git status`, and ask.
- **Never commit `vps.conf`, `stack/stack.env`, or `stack/apps/*.env`.** They
  are gitignored. If a command would add them, stop.
- **Do not run `docker system prune -a`.** It deletes the build cache for every
  image, which turns the next deploy into a fifteen-minute rebuild. Use
  `docker image prune -f`, which `ops/deploy.sh` already does.

## Where things are

```
/srv/vps-plus         this repo
/srv/repos            the four application checkouts
/srv/data             postgres volume, backups
/srv/skills-vault     the shared skills vault (symlinked into ~/.hermes and ~/.claude)
/var/lib/vps-plus     stage completion stamps
/var/log/vps-plus-*   bootstrap run logs
```

Containers are named `vpsplus-<app>`: `vpsplus-plus`, `vpsplus-studio`,
`vpsplus-trilux`, `vpsplus-nalar`, `vpsplus-postgres`.

## The app map

| key | repo dir | container port | what it is |
|---|---|---|---|
| `plus` | `plusthesite-` | 3000 | Next.js, `output: standalone` |
| `studio` | `studio-plusthesite` | 8787 | Vite SPA + Express AI proxy, one process |
| `trilux` | `trilux-design-page` | 8080 | static site bind-mounted; Express hosts its `api/` handlers |
| `nalar` | `new-nalar` | 3000 (published on 3001) | Next.js, no standalone build |

All four bind to `127.0.0.1` only. Nginx is the sole public listener.

## Common tasks

```bash
ops/status.sh                  # start here for anything that "seems broken"
ops/deploy.sh plus             # pull, rebuild, restart
ops/deploy.sh plus --no-pull   # rebuild the current checkout
ops/logs.sh studio 200
ops/psql.sh nalar
ops/backup.sh
sudo ./bootstrap.sh --force 80 # re-render nginx (then --force 90 for TLS)
```

## Diagnosing, in order

1. `ops/status.sh` — does the container run, does the local port answer, does
   the public URL answer?
2. Local port fails → the app is broken. `ops/logs.sh <app> 200`.
3. Local port works but the public URL does not → nginx or DNS.
   `sudo nginx -t`, then `tail /var/log/nginx/<app>.error.log`.
4. HTTPS fails but HTTP works → the certificate. `ops/status.sh` shows expiry;
   `sudo certbot certificates` shows the detail.
5. A build fails with no useful error → almost always OOM on a small VPS.
   `free -h`, `dmesg | grep -i oom`. Stage 70 builds serially for this reason;
   do not parallelise it.

## Build-time versus run-time environment

This trips people up more than anything else here.

`NEXT_PUBLIC_*` and `VITE_*` are **compiled into the browser bundle**. Changing
one in `stack/apps/<app>.env` and restarting the container does nothing — the
old value is still in the JavaScript. It needs a rebuild:
`ops/deploy.sh <app>`.

Everything else (`GEMINI_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `HACK_DB_*`) is
read per request, so a restart is enough.

`install/70-apps.sh` reads the public values out of the env files and passes
them as build args, so there is only ever one copy to edit.

## Before changing anything structural

Re-read `docs/MIGRATION-NOTES.md`. It records what is deliberately unfinished —
Trilux's Vercel Blob dependency, NALAR's missing standalone build, the MCP
servers still pointing at Windows paths — so you do not "fix" something that
was a considered trade-off, or assume something works that never did.
